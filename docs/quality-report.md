# React Native (Expo) App Starter: quality report

> **Where the code is.** The measurement scripts that produced these results are part of the source package, which is distributed separately (see [SOURCE-ACCESS.md](../SOURCE-ACCESS.md)). The raw results they wrote are included in this repository under [`results/`](../results/).

Version 0.1.0 by The Diamond Empire. This report states what was measured, how, what the numbers were, and what the checks cannot tell you. Every number in the results tables is generated by `npm run report:table` from files in [results/](../results/); none is typed by hand. Timing and performance scores are deliberately not measured: the machine that built this is shared and loaded, and timings from it would not mean anything.

**Read this first: the native iOS and Android apps were never run on a device, a simulator or an emulator.** None exists on the build machine. The app was verified through unit and component tests, a type check, lint, a web export (React Native Web) opened in Chrome, and the byte size of the native JavaScript bundles that `expo export` produces. Those bundles were exported and measured, never run. React Native on the web is not the same as the native app: web rendering differs from native, so browser results say little about keyboards, safe areas, gestures, the secure store or speed on a real phone.

## Verdicts

These sentences interpret the tables above; the tables are the source of truth.

- **Tests:** every suite passed in the clean-copy run (see the test table). The Jest suites use in-memory services; they show the logic and the components behave as written, not that a phone does.
- **Web export in Chrome:** every step of the main flow worked in all four viewport and scheme combinations, a signed-out visit to a protected address landed on the sign-in screen, choosing a theme changed the screen background and "System" followed the browser scheme again, no screen scrolled sideways, and the browser logged no console warnings or errors and made no failed or third-party request (only the local test server was contacted).
- **axe-core:** zero violations and zero "needs review" items on every scanned screen of the web export. This is a statement about the rules axe-core ran on the web export in one browser at four settings, not about the native apps and not about accessibility in general. Several real problems were found by earlier axe runs and fixed before the final run (see the change log).
- **Contrast from tokens:** every checked pair passes in both themes. This covers token pairs, not every pixel; axe-core also checked rendered colours on the web export.
- **Bundle sizes:** the web JavaScript, the web export as a whole and both Hermes bytecode bundles are well under the budgets. The budgets are deliberate ceilings written before anything was measured, so the large headroom says the starter adds nothing heavy; it does not say the sizes are small for every purpose. The native sizes are of exported bundles that were never run.
- **Third parties:** no URL to another host in source, no tracking or crash-reporting code, no network API call outside the HTTP adapter example, and no request to another origin in the browser.
- **Licences:** all 17 direct production dependencies are MIT. The wider tree has 23 entries outside the permissive set used by the check (MPL-2.0 CSS tooling, one CC-BY-4.0 data package, Unlicense and CC0 dedications, BlueOak-1.0.0, Python-2.0); they are listed with notes in `THIRD-PARTY.md` for a person to review.
- **ZIP:** identical bytes on two builds; no `node_modules`, results or build output inside.
- **Not verified at all:** anything on iOS or Android devices.

## Limits and threats to validity

- **The native apps were never run.** No device, simulator or emulator was available. Nothing here says the app launches, looks right or performs on iOS or Android. The secure-store path was tested only with a fake module; the AsyncStorage path ran only through Chrome's local storage (web) and was replaced by an in-memory store in the Jest tests. Gestures, keyboard avoidance, safe areas, the splash screen, deep links and dynamic type on a real phone were not seen.
- **Web rendering differs from native.** The browser checks run the web export through React Native Web: different elements, roles and focus behaviour than the native apps. A clean axe-core result on the web export does not carry over to VoiceOver or TalkBack.
- **Automated accessibility testing finds only part of the problems that affect people.** axe-core, contrast ratios and component assertions cannot judge whether labels are meaningful, whether the reading order makes sense, whether the wording is easy to understand, or how a screen works with a screen reader, a magnifier, speech input or switch devices. No screen reader was used for this report. Nothing here is a statement of conformance with the Web Content Accessibility Guidelines or any other standard.
- **"Needs review" results.** axe-core reports items it could not decide. The table counts them; they were not reviewed by a person for this report, so any such items are open.
- **One browser engine, four viewport and scheme combinations.** Chrome on Windows, headless, at 390 and 1280 px wide in the light and dark scheme. Other widths, 200 percent zoom, text-spacing overrides, Firefox and Safari were not tested. Dynamic type (a large system font) cannot be set in this setup; the component tests simulate the font scale only by mocking the window dimensions.
- **Contrast** covers a fixed list of token pairs. A new component with a new colour combination is not covered until its pair is added to `tools/contrast.mjs`.
- **Bundle sizes** are the sizes of exported files, not of an installed app, and say nothing about startup time or memory. The budgets were written before the first export (see the change log) and have not been changed.
- **The mock backend, not a server.** All app behaviour was exercised against the in-memory mock and a fake `fetch` for the HTTP adapter example. Token refresh, real rate limiting, account deletion and real error shapes are not covered.
- **Licence checking is tool-assisted, not legal advice.** The production tree includes Expo's command line tools, with a few packages outside the permissive set (see `THIRD-PARTY.md`); we did not verify which end up in the app bundles.
- **The GitHub Actions workflows (`ci.yml`, `verify.yml`) were never run**, and no EAS or other cloud build was started. `eas.json` is a skeleton.
- **Shared machine.** Other jobs were running during the work. This does not affect byte counts or pass/fail checks, which are deterministic, and is the reason no timings are reported.
- **Not measured:** load time, rendering performance, memory, battery, real-user behaviour, store review outcomes. No claim about any of these is made.

## Change log

Disclosure of reruns and changes made after something was measured or found. The final numbers come from the last run described in item 10.

1. **Budgets first.** `tests/budgets.json` was written before any `expo export` had been run for this project. Its values have not changed.
2. **Slow installs.** The first `npm install` took about 51 minutes on this shared machine inside a synchronised folder; the clean-copy `npm ci` at a short path took about six minutes. Nothing was skipped because of it.
3. **Router design change after tests failed.** The first app-level tests showed that the address "/" and addresses of screens a user may not open landed on the router's not-found screen when the guard was false. The fix was a root `index` route that redirects by auth state, moving the catalog tab to "/catalog", and a not-found route that redirects known screens to where the user belongs. This is a post-hoc design change made because a test failed.
4. **Exploratory axe runs changed the code.** Before the final run the web export was scanned several times on the development folder. axe-core found, and the code was changed for: content outside landmarks ("region": a `main` role on every screen, a navigation wrapper around the tab bar, and screens opened on top of the tabs now draw their own Back button and heading instead of the navigator header); catalog row names that did not contain their visible text ("label-content-name-mismatch": the row label was removed and the favourite heart is now an SVG instead of a text glyph); radios without a checked state ("aria-required-attr": `aria-checked` is set); the switch role and state set twice ("nested-interactive": the explicit role and state were removed from the switch); and hidden tab screens that stayed in the tab order ("aria-hidden-focus" and "needs review" colour contrast results: tab content is now hidden through `FocusGate` when its tab is not focused). The first exploratory scan also had a test-harness bug (hidden screens of a stack matched first), fixed in the script.
5. **Test bugs fixed.** A Windows glob in the Jest configuration matched no tests; the first double-tap test used overlapping act calls and broke later tests (it now holds the fake server's answer open); async polling inside `waitFor` also produced overlapping act calls; one expectation assumed the list renders all twelve items although the list renders only the first screenful. These were test problems, not app problems, except where item 3 or 4 says otherwise.
6. **Exploratory builds.** The web export was built several times and the native export once on the development folder before the final run. Those outputs were not recorded and are not used.
7. **First clean-copy run found tooling and test bugs, fixed afterwards.** `npm run test:record` recorded no counts for its Node-test suites because Node's path contains a space and the process was started through a shell, and a regular expression written with a single backslash inside a template string matched nothing; four documentation tests had mistakes (a mistyped regular expression, THIRD-PARTY.md wrongly held to the axe-limit rule, a wrong column index in the case-study check, and a fixed results path where the output directory can be moved). The results table also lacked a space after "Run:". These affect tests and table text only, not any measured quantity, so `npm run measure` was not run again; `npm run test:record` and `npm run report:table` were.
8. **Authoring.** The code was written in milestone order (M1 to M4) and the test suite was assembled alongside; the web and static suites and the measurement script (M5) were completed after the app code was feature-complete.
9. **A first complete clean-copy run was superseded.** The measurement set and the test record were first run from a clean copy as described in item 7. After that, the shipped tooling file `tools/lib/repo.mjs` gained two helper functions and the documentation tests were corrected, which changes the bytes of the customer ZIP and the count of static tests. Rather than patch the recorded numbers, the whole clean-copy sequence was run again and only that second run is recorded in `results/`. The first run's outputs were discarded.
10. **Final run.** From a clean copy at a short path (`npm ci`, `npm ci --prefix tools`, check:paths, typecheck, lint, jest, export:web, one `npm run measure`, report:table, test:record, report:table, test:static), with outputs written outside the copy and then copied into `results/`. The measurement window is in the Run line under the results tables.
